# 앱/웹 UX 검수 결과

웹으로 앱을 실제 구동해서(Expo web, 백엔드 연동 상태) 로그인부터 각 화면까지
직접 조작하며 확인한 내용. **어떤 상황에서 무엇이 부자연스러운지**를 기준으로 정리했다.
바로 고치지 않고 논의용으로만 기록한다.

## 🔴 치명적 — 첫 사용자가 갇힘

### 1. 인트로 "먼지 닦기" 오버레이에서 빠져나갈 수 없다

**상황**: 신규 가입 후 첫 로그인 → 홈 진입 시 전체 화면 오버레이가 뜬다.
"먼지를 닦아주세요 / 화면을 손가락으로 문질러 하자 진단 화면을 열어주세요."

**문제**
- **닫기·건너뛰기 버튼이 없다.** 문지르는 것 외에 탈출 경로가 없음
- **하단 탭까지 막는다.** 홈/진단/커뮤니티/더보기 어느 것도 눌리지 않음
- 웹에서 화면 전체를 8번 문질러도 열리지 않았다 (마우스 드래그로는 임계치 미달)
- 안내 문구가 "손가락으로"라서 웹/태블릿 맥락과 맞지 않음

**영향**: 웹에서 시연하면 첫 화면에서 막힌다. 발표·심사 때 치명적.
모바일에서도 스킵이 없어서 "빨리 써보고 싶은" 사용자에게 강제 인터랙션이 된다.

**참고**: 인트로 노출 여부 플래그(`markDustIntroSeen`)는 **로그인 시점에 미리 저장**되므로
한 번 갇히면 재로그인 후엔 안 뜬다. 즉 "첫인상"만 정확히 망가진다.

`frontend/app/(tabs)/index.tsx` (Modal + PanResponder), `frontend/app/login.tsx:51-53`

## 🟠 주요

### 2. 더보기 서랍이 40px 폭으로 깨져서 열린다

**상황**: 웹/태블릿 등 넓은 화면에서 하단 "더보기" 탭을 누를 때.

**문제**: 패널이 300px여야 하는데 실제 **40px**로 렌더된다.
제목이 "더/보/기"로 세로로 쪼개지고 메뉴 항목을 읽을 수 없다.

**원인**: `PANEL_WIDTH`를 **모듈 로드 시점에 한 번만** 계산한다.
```
const PANEL_WIDTH = Math.min(300, Dimensions.get("window").width * 0.8);
```
화면 크기를 아직 모르는 시점에 값이 고정되고, 이후 리사이즈·회전에도 갱신되지 않는다.

**영향**: 웹/태블릿에서 항상 깨진다. (폰 해상도에서는 계산값이 우연히 300 으로 맞아 표시는 정상이지만,
화면 크기를 한 번만 읽고 고정하는 구조 자체가 깨지기 쉬운 형태다.)

`frontend/src/components/MoreDrawer.tsx:18`

### 3. ~~사진 5장을 올려도 1장만 분석된다~~ ✅ 수정 완료

**상황**: 업로드 화면이 "0 / 5", "최대 5장까지 다양한 각도에서 등록 가능합니다"라고 안내.
사용자가 하자를 여러 각도로 찍어 5장 등록 → 진단 시작.

**문제**: 실제로는 **첫 장만 서버로 전송되고 나머지 4장은 조용히 버려진다.**
```
// 첫 번째 이미지 사용
const uri = images[0];
```
백엔드도 `MultipartFile image` 단일 파일만 받는다.

**영향**: "여러 각도로 찍으면 더 정확하겠지"라고 믿고 공들인 사용자의 기대를 배신한다.
버려진다는 안내조차 없어서 사용자는 끝까지 모른다.

**조치**: 등록한 사진을 전부 서버로 보내고, LLM 이 **한 번의 호출로 모두 종합 분석**하도록 수정했다.
장별로 따로 세지 않고 하나의 결과로 합치도록 프롬프트에도 명시. 사진 3장 실제 전송 검증 완료
(prompt_tokens 725 → 1297 로 증가, 결과는 중복 없이 1건으로 종합).

`frontend/src/api/diagnosis.ts`, `DiagnosisController`, `DiagnosisOrchestrator`, `LlmVisionDetector`

### 4. 자동 로그인이 없다 — 앱을 켤 때마다 다시 로그인

**상황**: 로그인했던 사용자가 앱을 껐다 켜거나, 웹에서 새로고침할 때.

**문제**: 진입 라우트가 **조건 없이 로그인 화면으로** 보낸다.
```
export default function Index() { return <Redirect href="/login" />; }
```
로그인 화면에도 기존 토큰을 확인하는 로직이 없다.
토큰은 `AsyncStorage`에 멀쩡히 남아있는데도 매번 아이디/비밀번호를 다시 입력해야 한다.

**영향**: 재방문 비용이 매번 발생. 앱에서 가장 흔한 이탈 지점 중 하나.

`frontend/app/index.tsx`, `frontend/app/login.tsx`

### 5. 홈의 하자 유형 칩을 눌러도 선택이 전달되지 않는다

**상황**: 홈 상단의 `곰팡이 / 누수 / 균열 / 박리 / 부식 / 들뜸` 칩 중 "곰팡이"를 누름.

**문제**: 진단 업로드 화면으로 이동은 하지만 **곰팡이가 선택된 상태가 아니다.**
업로드 화면의 6개 타일은 "진단 가능 범위"라는 **정보 표시일 뿐 선택 UI가 아니다.**

**영향**: 칩이 필터/선택처럼 생겨서 "곰팡이를 진단하겠다"는 의도를 표현했다고 느끼는데,
그 의도가 어디에도 반영되지 않는다. 사용자는 자기 선택이 무시됐다고 느낀다.

`frontend/app/(tabs)/index.tsx` (칩) → `frontend/app/upload.tsx`

### 6. 지역 체계가 두 갈래로 갈라져 있다

**상황**: 커뮤니티 "지역별" 탭과 업체 검색의 지역 필터를 각각 쓸 때.

| | 범위 | 단위 |
|---|---|---|
| 커뮤니티 | 전국 시/도 전부 | 시/군까지 (경기도 > 수원시) |
| 업체 검색 | **8개 광역만** | 광역시/도 단위 |

업체 검색은 `["서울","경기","인천","부산","대구","광주","대전","울산"]` 뿐이라
**강원·충청·전라·경상·제주 사용자는 자기 지역으로 업체를 찾을 수 없다.**
명칭도 다르다 ("경기도" vs "경기").

**영향**: 같은 앱 안에서 지역 고르는 방식이 화면마다 달라 일관성이 깨진다.
지방 사용자에겐 기능 자체가 비어 보인다.

`frontend/src/constants/regions.ts` vs `frontend/src/api/experts.ts:4`

## 🟡 중간

### 7. 진단 대기 화면에 진행률이 없고 취소도 못 한다

**상황**: 사진 올리고 "진단 시작하기" → 분석 대기 화면.

**측정값**: LLM 전환 후 실제 **10~14초** 소요 (비전 호출 + 가이드 생성 2회).

**문제**
- 진행률·단계 표시가 없고 문구만 순환한다 ("위험도 분석을 진행하고 있어요" 등)
- 안내가 **"몇 초에서 수십 초"** 로 모호하다. 10초가 걸릴지 40초가 걸릴지 모름
- **취소 버튼이 없다.** 잘못 올렸어도 끝날 때까지 기다려야 함
- 타임아웃이 180초라, 서버가 느리면 3분간 갇힐 수 있음

**영향**: 10초는 로딩 스피너만 보기엔 긴 시간이다. 이탈·중복 실행 유발.

`frontend/app/analyzing.tsx`, `frontend/src/api/diagnosis.ts:126`

### 8. 업로드 화면 안내문이 LLM 전환 이후와 맞지 않는다

**상황**: 업로드 화면 하단 "촬영 팁".

- "현재 AI는 **6가지** 하자 유형을 기준으로 분석하며, 그 외 문제는 정확히 인식되지 않을 수 있습니다"
  → LLM 전환 후 실제로는 11종 + 그 외도 설명 가능
- "진단은 한 번에 **한 가지** 하자 유형만 가능합니다"
  → LLM은 한 사진에서 최대 5개까지 반환한다

**영향**: 실제보다 기능을 좁게 안내해서 사용자가 시도 자체를 안 하게 만든다.

`frontend/app/upload.tsx`

### 9. 홈 통계가 하드코딩된 가짜 숫자다

**상황**: 홈 중단 "10,000+ 진단 완료 / 5.0 ★ 전문가 평점 / 99% 고객 만족도".

**문제**: 실제 데이터가 아니라 코드에 박힌 상수다.
```
const STATS = [
  { value: "10,000+", label: "진단 완료" },
  { value: "5.0 ★",   label: "전문가 평점" },
  { value: "99%",     label: "고객 만족도" },
];
```
특히 "5.0 ★"과 "99%"는 현실적으로 나올 수 없는 수치라 오히려 의심을 부른다.

**영향**: 시연·심사에서 "이 숫자 근거가 뭐냐"는 질문이 나오기 쉽다.
실제 집계로 바꾸거나, 당장 어렵다면 섹션을 빼는 편이 안전하다.

`frontend/app/(tabs)/index.tsx:176`

### 10. 심각도와 위험도 등급이 서로 안 맞아 보인다

**상황**: 진단 결과에서 곰팡이 1건이 `severity=MEDIUM`으로 판정됐는데
화면의 위험도는 **HIGH (80점)** 으로 표시된다.

**원인**: 위험도 공식이 지수함수(`1 - exp(-raw * 2.5)`)라 빠르게 포화된다.
면적이 조금만 커도 대부분 HIGH 구간으로 올라간다. (LLM 전환 이전 YOLO 시절에도 동일)

**영향**: 사용자가 보기엔 "보통이라며 왜 높음이지?"로 읽힌다. 등급 신뢰도가 떨어진다.

`backend/.../diagnosis/service/RiskCalculator.java`

## 📱 모바일 화면(375×812)에서 추가로 확인한 것

### 11. 탭 화면 3개에서 맨 아래 콘텐츠가 탭바에 영구히 가려진다

**상황**: 홈/진단/커뮤니티 탭에서 끝까지 스크롤했을 때.

스크롤 영역의 아래 여백이 그보다 훨씬 작다.

|---|---|---|
| 홈 | `paddingBottom: 8` | 약 82px 가려짐 |

| 커뮤니티 | `paddingBottom: 14` | 약 76px 가려짐 |

**확인 방법**: 홈에서 끝까지 스크롤해도 "서비스 소개" 카드 아랫부분이 잘린 채로 더 이상 내려가지 않는다.

**영향**: 스크롤을 다 내렸는데도 안 보이는 영역이 있어서 사용자는 "여기가 끝인가?" 하고 헷갈린다.
히스토리 화면이 이미 올바른 값(100)을 쓰고 있으므로 나머지도 맞추면 된다.

## 🖥 데스크탑에서 웹(company-web)을 보며 확인한 것

### 15. 예약 날짜 기본값이 UTC 기준이라 오전에 하루 어긋난다

**상황**: 업체가 파트너 센터에서 예약/수리완료 날짜를 다룰 때.

```
function todayString() {
    return new Date().toISOString().slice(0, 10);   // ← UTC 날짜
}
```
`toISOString()` 은 항상 UTC 를 돌려주므로, **한국 시간 00:00~09:00 사이에는 "어제" 날짜가 기본값으로 잡힌다.**

이 값이 조회 기준 날짜(`selectedDate`)와 **수리 완료일(`repairCompletedDate`) 기본값**에 함께 쓰인다.
업체가 아침에 수리 완료 처리를 하면 완료일이 하루 전으로 저장될 수 있다.

`company-web/src/pages/company/CompanyReservationsPage.jsx:10`, `ReservationDetail.js:5`

### 16. 같은 이유로 관리자 화면 시각/날짜도 어긋난다

- `AdminUserDetailPage.jsx:50` — `toISOString().slice(0,16)` 으로 **시각을 UTC 로 표시** (한국 시간과 9시간 차이)
- `AdminReviewsPage.jsx:96` — 날짜만 UTC 로 표시. 한국 시간 새벽에 쓴 리뷰가 **하루 전 날짜로** 보인다

반면 고객센터·쪽지 화면은 로컬 시간(`getFullYear()` 등)으로 표시한다.
**같은 관리자 웹 안에서 화면마다 기준 시간대가 다르다.**

### 17. 날짜 포맷 함수가 화면마다 복사되어 있다

`formatDate` / `formatTime` / `formatCreatedAt` 같은 함수가
**company-web 7개 파일, 앱 11개 파일에 각각 따로 정의**되어 있다.
15·16번 같은 불일치가 계속 생기는 구조적 원인이다. 공용 유틸로 모으는 게 맞다.

### 18. 관리자 웹에 지금 누구로 로그인했는지 표시가 없다

사이드바에 계정 정보가 없어서, 관리자 계정인지 업체 계정인지 화면만 봐서는 알 수 없다.
계정을 여러 개 두고 테스트할 때 특히 헷갈린다.
